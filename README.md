# NetQuest — клиенты для лабораторной работы

Сервер: `153.76.167.185`. Нужен Python 3, используется только стандартная
библиотека (`socket`, `struct`, `time`, `re`, `statistics`).

Каждый клиент принимает ID (фамилия латиницей, приводится к нижнему регистру)
первым аргументом и печатает ответ сервера с флагом.

| Задание | Порт | Запуск |
|---|---|---|
| 1. math    | 7001/tcp | `python task1_math.py <id>` |
| 2. bytes   | 7002/tcp | `python task2_bytes.py <id>` |
| 3. latency | 7003/tcp | `python task3_latency.py <id>` |
| 4. udp     | 7004/udp | `python task4_udp.py <id>` |
| 5. frames  | 7005/tcp | `python task5_frames.py <id>` |

`common.py` — общий код: адрес сервера, разбор аргумента и класс `Conn`
(TCP-соединение со своим буфером). Один `recv()` не равен одному `send()`
на сервере, поэтому всё полученное складывается в буфер, и уже из него
вырезаются строки (`read_line`) или ровно N байт (`read_exact`).

## Как устроены клиенты

1. **math**: регулярным выражением находим в буфере `Q n/100: a op b = ?`
   и отвечаем одним числом в строке. `/` — целочисленное деление (`//`),
   `%` — остаток.
2. **bytes**: читаем до `BEGIN\n`, учитываем байты, пришедшие в том же
   `recv` после `BEGIN`, затем считаем всё до 3 секунд тишины
   (`settimeout(3)`). Данные бинарные, поэтому строки не ищем, а только
   считаем длину.
3. **latency**: 20 TCP-подключений для замера сетевой задержки, затем 60
   пар PING/PONG, ответ = `min(PING RTT) − min(RTT сети)` (см. ниже).
4. **udp**: отправляем `GET <id>`, собираем куски в словарь `seq → данные`
   (дубли отбрасываются, порядок не важен), затем просим `RESEND` для
   недостающих, пока сообщение не соберётся целиком.
5. **frames**: заголовок кадра `struct.Struct("!2sBI")` — magic, type,
   length (7 байт, big-endian). Читаем ровно 7 байт заголовка, затем ровно
   `length` байт payload. Кадры NOISE (бывают и пустые) пропускаем, на
   QUESTION отвечаем кадром ANSWER с `int64`.

## Вопрос из задания 3: какой характеристикой оценивать постоянную задержку

Каждое измерение = **сеть + постоянная часть + джиттер**, где джиттер ≥ 0
и иногда очень большой. Шум только *добавляется*, он не может сделать
ответ быстрее постоянной части.

- **Среднее** не подходит: оно всегда больше постоянной части на средний
  джиттер, а редкие огромные выбросы сдвигают его ещё сильнее (в нашем
  прогоне min ≈ 258 мс, mean ≈ 281 мс, max ≈ 586 мс).
- **Медиана** устойчива к выбросам, но тоже смещена вверх: это
  «постоянная часть + типичный джиттер» (≈ 271 мс).
- **Минимум** — лучшая оценка. Раз джиттер неотрицательный, самый быстрый
  ответ — тот, в котором джиттер был почти нулевым. Чем больше замеров, тем
  ближе минимум к истинному значению. Поэтому замеров нужно не меньше 20.

**Сравнение с ping.** Утилита `ping` показывает min/avg/max, и для оценки
«чистой» задержки канала тоже смотрят на min. Но важно, *что* измеряется.
`ping` (ICMP) и TCP-рукопожатие измеряют только сеть: им отвечает ядро
сервера, без искусственной задержки. PING/PONG в задании проходит через
приложение и включает сеть плюс задержку сервера. На практике первая
попытка `ANSWER = min(PING RTT) = 259` была отклонена: в нём сидели ~24 мс
сетевого RTT. Поэтому клиент отдельно измеряет RTT сети временем
`connect()` (аналог ping, но по TCP на тот же порт) и вычитает его
минимум. Получилось 258 − 24 ≈ 234 мс, сервер принял ответ (допуск ±5 мс).
Сетевой RTT сам шумит (24–60 мс), поэтому и для него берётся минимум, а не
среднее.
